# Проверка поставляемого технического ядра

Для новой копии проекта есть одна автономная команда, которая проверяет сохранённые пакеты и действующие команды назначения меток. Доступ к исходной панели, скачивание источников и повторное обучение не нужны.

Из корня репозитория в среде `requirements.txt`:

```sh
python -m scripts.verify_technical_core --output artifacts/technical-acceptance.json
```

Файл отчёта должен быть новым и находиться вне проверяемых каталогов `reports`. Для другой копии проекта передайте `--root <путь-к-копии>`. Её модули и команды должны быть доступны в этой копии; расчёт использует тот же Python, которым запущена проверка. Команда ограничивает число потоков; дочерние процессы Windows работают с приоритетом BelowNormal.

Проверка охватывает:

- Четыре пакета `model-frontier-2026-10-03`, `temporal-core-2026-10-03`, `economic-generalization-2026-10-03` и `core-round3-review-2026-10-03`: все перечисленные файлы, SHA-256, размеры при наличии и полноту покрытия. Пути обязаны оставаться внутри заявленного каталога. Изменённые, пропущенные и неучтённые файлы приводят к отказу. Повторная сверка после предсказаний обнаруживает изменение пакета во время выполнения.
- Точное воспроизведение 6 048 годовых меток: три сохранённых правила × 2 016 опубликованных профилей. Проверяются полные правила KMeans4, Ordinary и Huber75.
- Все 12 опубликованных месячных пакетов 2024 проверяются тем же `validate_reference_packet`, который используется при предсказании: формат и обязательные поля, контрольная сумма, связь с объявленным референсом, IDs/региональное покрытие, пять координат и согласованные интервалы поправки. Публичные метаданные содержат необходимые ID, регионы и контрольную сумму референса. Полные базовые месячные признаки и текущие исходные строки остаются частными: фактическую медианную поправку по ним команда не пересчитывает и контрольную сумму полного референса из усечённых метаданных не восстанавливает.
- Реальный запуск `predict_frozen` для месячного и годового режима, трёх `predict_frontier`, трёх `predict_temporal` и `predict_dual` для создания референса, пакета и предсказания. Небольшой искусственный CSV строится из сохранённых центров и калибровки. Результаты сверяются с контрактом API; это проверка совместной работы ввода, форматов моделей и CLI, а не повторение национального эксперимента.
- Отказ парного CLI при неверном закреплённом хеше и существующем выходном файле проверяется по конкретному классу исключения и устойчивому тексту причины. При неверном хеше новый файл должен отсутствовать; при существующем выходе его байты должны остаться точными. Отсутствующая зависимость/модуль, ошибка вызова или таймаут дают `SETUP_ERROR` и код 2; иной неожиданный отказ не засчитывается как успешный контроль. Хеши текущих модулей назначения сохраняются в отчёте и сверяются до/после исполнения.

Исторические манифесты связывают документы и исходники со своим расчётным снимком. Изменение современной документации или текущего исходника относительно такого снимка отдельно отмечается как `CURRENT_DOCUMENTATION_DRIFT` или `CURRENT_SOURCE_DRIFT`. Это наблюдение не считается порчей исторического пакета. Исходники внутри самих пакетов остаются неизменяемыми и проверяются наравне с другими файлами.

Для проверки одних файлов достаточно стандартной библиотеки Python:

```sh
python -m scripts.verify_technical_core --integrity-only --output artifacts/technical-integrity.json
```

Этот режим возвращает `PASS_INTEGRITY_ONLY`, а поле `predictions.status` равно `NOT_RUN`. Его нельзя выдавать за успешное применение моделей.

| Код выхода | Значение | Действие |
|---|---|---|
| 0 | `PASS` или явно ограниченный `PASS_INTEGRITY_ONLY` | Прочитать область проверки и наблюдения в JSON |
| 1 | Нарушен контракт пакета либо предсказаний | Восстановить точный файл/пакет или исправить указанную несовместимость; не переписывать старый манифест под новые данные |
| 2 | Ошибка запуска, зависимостей, таймаут CLI либо недопустимый выход | Проверить среду, выбранный корень и новый выходной путь |

Отчёт содержит манифесты, количества файлов/меток, хеши применённого исходного кода и результаты вызовов CLI. Временные искусственные данные удаляются. Проверка не даёт криптографической подписи автора: согласованная подмена файла вместе с его манифестом требует внешней доверенной привязки. Она также не оценивает экономическое превосходство, достоверность территориальных переходов, производственную типологию, официальный смысл MQ или перенос на будущие данные. Научный статус остаётся указанным в [основном отчёте](REPORT_RU.md), [временном контракте](TEMPORAL_CORE.md) и [экономической проверке](ECONOMIC_GENERALIZATION.md).

Для изменения самой проверочной команды:

```sh
python -m unittest discover -s tests -p test_technical_acceptance.py -v
```

Адресные тесты проверяют подменённые/пропущенные файлы, небезопасные пути, ошибочные хеши, неполный манифест, повторный выход и изменение пакета между фазами. Заново запечатанные пакеты с неизвестной ревизией, отсутствующим обязательным полем, неверной размерностью или обратным интервалом отклоняются каноническим валидатором. Реальные дочерние Python-процессы проверяют допустимую причину отказа, сохранность/отсутствие выхода, отсутствующие модули и различие кодов 1/2. Для точного повторения подготовки исходной панели и национальных расчётов используются отдельные команды [REPRODUCE.md](REPRODUCE.md).


## Проверка дополнительного модуля, 6 октября 2026

Итоговая техническая сборка сохраняет прежние модели и добавляет непрерывное описание. Новый запуск `python -m scripts.verify_continuous_core` требует подготовленную панель расходов и её фиксированный хеш, сохранённую модель и её фиксированный хеш. Он вызывает итоговую команду для 2023/2024 и сравнивает все назначения обеих моделей с действующим исходным кодом. Обучение и чтение экономических исходов не выполняются. [Точные команды](CONTINUOUS_CORE.md) · [результаты итоговой сборки](../reports/continuous-core-2026-10-06/README.md). Старые проверки ядра выполняются отдельно и сохраняют прежние правила.
